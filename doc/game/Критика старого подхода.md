# Критика старого подхода

## Три базы данных

Разделение на `base.db`, `literary.db` и `<slug>.db` выросло из заблуждения,
что у каждой базы должен быть один хозяин, и поэтому их надо развести по
файлам. Права записи всё равно проверяются по таблицам, а не по файлам, так
что разделение ничего не даёт. Зато две базы нельзя изменить одной
транзакцией: в режиме WAL она не охватывает два файла, поэтому
согласованность приходится держать кодом — повторными проверками и
уникальными индексами. Это и есть цена оверинжиниринга.

## deferred_events → очередь go-wex

Это не критика старого решения, а смена механизма. В старой версии срок
лежал строкой в `deferred_events`: вид, тело, срок, статус. В новой сборке
разовый срок — работа очереди (`jobs.Request` с `NotBefore`), повторяющийся —
событие (`events.Rule` с периодом), которое ставит работу на каждый срок.
Средств go-wex хватает: есть срок, тело, отмена, повтор, предел попытки,
ключ живой работы и догон после простоя.

Чего нет, и это решается в модуле, а не в движке:

- **Истории срабатываний очередь не хранит.** После `Done` работа уходит,
  `List` показывает только живые. След должен остаться доменным событием
  в таблице `events`, иначе от срабатывания не будет записи.
- **`Done` и эффект — не одна транзакция.** Если обработчик записал эффект
  и упал до `Done`, работа повторится и эффект может задвоиться. Обработчик
  должен быть идемпотентным: проверка перед записью или уникальный ключ
  в `events`.
- **Пропущенные сроки не разворачиваются.** Служба событий при простое даёт
  одно срабатывание и сдвигает срок к первому будущему. Старая таблица
  хранила строку на каждый срок, и срабатывание шло по каждой. Если
  игровому правилу нужно N срабатываний за пропущенные дни, это N работ,
  а не одно событие.
- **Срок в очереди — реальное время.** Для срока по игровым часам
  `NotBefore` считается при постановке; очередь всё равно сработает по
  реальным часам.
- **Модулю нужен доступ к постановке.** Разборщик передан модулю моделей,
  а модулю мира — нет; пока работа из мира не ставится.

Вывод: для разового срока и повтора механизма достаточно, но срабатывание
обязано оставлять доменное событие, а обработчик — быть идемпотентным.
Разница в пропущенных сроках — единственное место, где старое поведение
не воспроизводится один в один.
