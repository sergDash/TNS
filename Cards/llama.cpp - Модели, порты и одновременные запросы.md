# Как llama-server работает с моделями, портами и одновременными запросами

Проверено на сборке llama.cpp `b12063` (сервер сообщает `0.8.0-dev`, коммит `2cbca389f`), CPU-only: `--list-devices` отвечает `(none)`. Машина 16 ядер, 123 ГБ памяти, модели Qwen2.5-7B-Instruct-Q4_K_M (4,4 ГБ), Qwen3.5-9B-abliterated Q4_K_M (5,3 ГБ) и bge-m3-Q8_0 (606 МБ). Все числа ниже — с этой машины; на другой они будут другими, но устройство то же.

## Один процесс — одна модель

`llama-server --model X --port N` поднимает один экземпляр, который держит одну модель и слушает один порт. Две модели означают два процесса и два порта. Именно так устроен оригинальный TNS: генерация на `:5001`, эмбеддинги на `:5002`, каждый под своим надзирателем.

Это не свойство llama.cpp, а следствие выбранного способа запуска. Ниже — то, что сервер умеет сверх этого.

## Роутер: один порт на несколько моделей

Если запустить `llama-server` без модели, указав каталог или файл пресетов, сервер работает роутером:

```sh
llama-server --models-dir /path/к/моделям --port 8798 --models-max 2
llama-server --models-preset models.ini --port 8798 --models-max 2
```

Публичный порт один. На каждую модель роутер поднимает дочерний `llama-server` на случайном порту и проксирует запросы к нему. В опыте на порту 8798 жили две модели, а дочерние процессы слушали 46723 и 52847; их родитель — процесс роутера. Запрос маршрутизируется полем `model` в теле POST-запроса и параметром `?model=` у GET.

| Аргумент | Что делает |
|---|---|
| `--models-dir PATH` | каталог с файлами `.gguf` как источник моделей |
| `--models-preset PATH` | INI-файл с настройками на каждую модель |
| `--models-max N` | предел одновременно загруженных моделей, по умолчанию 4, `0` — без предела |
| `--models-autoload` / `--no-models-autoload` | загружать ли модель при первом запросе (по умолчанию загружать); можно задать `?autoload=false` на отдельный запрос |
| `--models-memory-margin N` | выгружать по памяти (см. ниже) |

## По одной модели или по две

Предел задаёт `--models-max`. Проверено с `--models-max 1`: запрос к `bge-m3` загрузил её и выгрузил `qwen25-7b`, следующий запрос к `qwen25-7b` выгрузил `bge-m3` и загрузил его. То есть «держать одну модель за раз» — это настройка запуска, а не ограничение реализации. С `--models-max 2` обе модели висели загруженными одновременно и отвечали каждая на свой тип запроса.

## Пресеты: разные настройки разным моделям

Пресет — INI-файл, секция на модель, ключи совпадают с аргументами командной строки без ведущих дефисов. Секция `[*]` задаёт общие значения.

```ini
version = 1

[*]
ctx-size = 2048
metrics = 1

[qwen25-7b]
model = /path/Qwen2.5-7B-Instruct-Q4_K_M.gguf

[bge-m3]
model = /path/bge-m3-Q8_0.gguf
embeddings = true
pooling = cls
```

Кроме аргументов, у пресетов есть свои ключи: `load-on-startup` (грузить ли модель при старте сервера) и `stop-timeout` (сколько ждать при выгрузке перед принудительным завершением, по умолчанию 10 с). Аргументы, которыми управляет роутер (хост, порт, ключ API), у экземпляров перезаписываются.

## Эмбеддинги и генерация — два экземпляра

`--embeddings` не добавляет эндпоинт, а переводит экземпляр в режим только эмбеддингов. Запрос `/v1/embeddings` к экземпляру без этого флага вернул 501 «This server does not support embeddings. Start it with `--embeddings`». Значит экземпляров нужно два, но портов может быть один: роль задаётся пресетом, а роутер прячет детей. В опыте на одном порту 8798 успешно работали и `/v1/embeddings` для `bge-m3`, и `/v1/completions` для `qwen25-7b`.

## Одновременные запросы

Число слотов у одного экземпляра задаёт `-np/--parallel`; по умолчанию `-1`, и сервер сам выбрал 4 слота. Запросы к одной модели обслуживаются пакетом, а не строго по очереди:

- один запрос на 64 токена — 8,8 с;
- два одновременных запроса по 64 токена — каждый 9,38 с при 6,72 ток/с, оба завершились за 9,7 с.

Суммарная пропускная способность выросла, скорость каждого запроса упала. Последовательная обработка — это `--parallel 1`, тоже настройка.

Разные модели в режиме роутера — это разные процессы, и они действительно считают одновременно, но выигрыша на одном процессоре не дают. Два запроса по 48 токенов к 7B и 9B:

| Порядок | Время | Скорость каждого |
|---|---|---|
| по очереди | 15,0 с | 7–8 ток/с |
| одновременно | 15,4 с | 3,84 и 3,15 ток/с |

Итог тот же, задержка каждого запроса вдвое хуже: процессы делят одни и те же ядра. Держать две генеративные модели сразу имеет смысл только ради готовности к переключению, а не ради скорости. Разные по назначению экземпляры (векторы и генерация) полезны тем, что короткий запрос к векторной модели не ждёт длинную генерацию в общей очереди.

## Память: управление есть, но не на процессоре

`--models-memory-margin N` заставляет роутер выгружать модели по LRU, пока новая не поместится, оставляя N МиБ свободными на каждом устройстве. Замер делает короткоживущий дочерний процесс при старте: `min`, `max` и, после загрузки, фактически занятая память `effective` — они видны в поле `memory` у модели в `GET /models`.

На CPU-only сборке этого нет. `--list-devices` отвечает `(none)`, поле `memory` остаётся `null`, а в документации прямо сказано: память хоста считается неограниченной, на сборке без устройств ограничение не действует. Поэтому на целевом слабом компьютере предел остаётся только по числу моделей (`--models-max`), а решение «сколько держать» принимает приложение.

## Что сервер сообщает сам

Для калибровки не нужно ничего, кроме ответов сервера:

- `timings` в ответе на генерацию: `prompt_per_second` и `predicted_per_second`;
- `GET /metrics` при запуске с `--metrics`: те же скорости счётчиками;
- `GET /models`: статус `loaded` или `unloaded` у каждой модели — по нему видно, что загрузка закончилась;
- `GET /models/sse`: событие `model_memory`, когда замер памяти завершён.

Холодный старт 7B Q4 на этой машине — около 2,6 с: запрос с одним токеном холодным занял 2,78 с, он же на загруженной модели — 0,14 с. Скорости при настройках по умолчанию (число потоков не задавалось): префил 35 ток/с, генерация 7,4–8 ток/с у 7B Q4.

## Что из этого следует

Схема «две фиксированные службы на двух портах», принятая в оригинальном проекте, — один из вариантов, и он выбран запуском двух независимых процессов, а не навязан llama.cpp. Доступны как минимум три конфигурации:

1. Два процесса на двух портах — то, что есть сейчас.
2. Один роутер с `--models-max 2` — один порт, обе модели загружены, каждая отвечает на свои запросы.
3. Один роутер с `--models-max 1` — один порт, одна модель за раз, переключение с выгрузкой.

Число одновременных запросов задаётся `--parallel`, а не архитектурой. Ограничение по памяти на процессорной сборке не работает, поэтому число удерживаемых моделей на слабой машине остаётся решением приложения, а не сервера. А замеры говорят, что вторая генеративная модель скорости не даёт, поэтому практический набор — одна генерация плюс векторы; как их разместить, двумя портами или роутером, — дело выбора.

## Как повторить

```sh
mkdir -p /tmp/rmodels
ln -s /path/Qwen2.5-7B-Instruct-Q4_K_M.gguf /tmp/rmodels/qwen25-7b.gguf
ln -s /path/bge-m3-Q8_0.gguf /tmp/rmodels/bge-m3-Q8_0.gguf

llama-server --models-dir /tmp/rmodels --port 8798 --models-max 2
curl -s localhost:8798/models
curl -s localhost:8798/v1/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen25-7b","prompt":"Одно слово","max_tokens":4,"temperature":0}'
```

Если рядом со сборкой лежат библиотеки без символических ссылок вида `.so.0`, сервер не запустится с «cannot open shared object file». Лечится каталогом со ссылками на `.so.0.8.0` и `LD_LIBRARY_PATH`.
